# SQLi: login bypass

## Что за уязвимость
Приложение проверяет вход запросом, который собирает склейкой строк: логин и пароль
подставляются прямо в текст запроса. Поэтому ввод пользователя попадает не только
в значение, но и в структуру запроса, и атакующий может изменить саму логику проверки.

## Как выглядит уязвимый запрос
```sql
SELECT * FROM users WHERE username = 'wiener' AND password = 'bluecheese'
```
Вход проходит, если база нашла строку, где совпали и логин, и пароль.

## Payload и разбор
Логин `administrator'--`, пароль любой непустой. Получается запрос:

```sql
SELECT * FROM users WHERE username = 'administrator'--' AND password = ''
```
Кавычка после `administrator` закрывает строку раньше времени. `--` начинает комментарий:
база не читает всё после него, то есть `' AND password = ''`. Остаётся
`WHERE username = 'administrator'`. Условие на пароль пропало, база вернула строку
администратора, приложение решило, что вход выполнен.

Ввод `administrator` + пароль `" "` не сработал: в нём нет `'--`, комментария нет,
условие на пароль осталось. Двойные кавычки внутри строки в одинарных кавычках
обычные символы, поэтому база искала пароль из трёх символов `" "`. Такого нет.

## Что не понял сам
Не понимал, почему `administrator'--` с пустым паролем не пропускает. Предположил, что
пустое поле отклоняет форма ещё до отправки. Это гипотеза, не проверено:
F12, поле пароля, есть ли атрибут `required`.

## Как чинится в коде
Значения передаются в базу отдельно от текста запроса (параметризованный запрос):
`... WHERE username = ? AND password = ?`, значения вторым аргументом. База разбирает
структуру до получения значений, поэтому `administrator'--` попадает в поле как обычная
строка. База ищет пользователя с именем из 16 символов `administrator'--`. Такого нет,
вход отклонён.

Запретить символ `'` в форме не исправление: ломаются честные данные (фамилия O'Brien),
а причина, склейка, остаётся.
